# Editor private backup workflow

The Projects workspace includes Cloud backups. A deployment must route same-origin /v1/projects requests to the existing private authenticated backup service. The editor never accepts arbitrary service URLs or saves the credential; the user supplies a short-lived access token in memory. The client uses explicit bearer authorization, no cookies, no redirects and no-store fetches. There is no automatic upload or public cloud provisioning.

Refresh history first; save uses the observed head revision in If-Match and requires explicit confirmation. A 409 conflict clears the local history/review and requires refresh. Historical downloads are bounded, checked against the server ETag and independently SHA-256 hashed, then validated by the existing project parser before review. Opening a verified backup changes only the local project through normal undoable editor history. Restoring appends a new remote revision and leaves the local project unchanged. Both operations require explicit confirmation. Read-only identities may inspect/open but cannot write. Clearing credentials removes the in-memory token, history and review.

The two-browser regression uses the actual loopback backup HTTP server, synthetic signed RSA access tokens, two tenant identities plus a read-only identity, and a real private temporary filesystem store. It checks save, restore, integrity metadata, review/open, stale-write rejection, cross-tenant isolation, read-only denial and credential clearing. Vite proxies the same-origin endpoint only in that test. This is not real cloud storage, external login or production security acceptance. The separate cloud adapter and live acceptance drill remain as documented in backup-service.md.
