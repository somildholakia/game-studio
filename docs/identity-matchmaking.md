# Identity-bound matchmaking reference service

This private service runs the shared static-course simulation from the same TypeScript runtime as the editor. It is independent of Vite development middleware and anonymous room codes. It pairs two authenticated users on the same tenant and operator-approved course. The server assigns random ticket and racer identifiers, owns all movement/collection/winner state, and requires the verified identity on every request. Client-supplied tenant, identity, score and position claims are rejected or ignored; no actual subject identifier is returned to peers. A user has at most one active queue/match ticket. Tenant/global capacity, membership expiry, match lifetime and bounded fixed-step catch-up constrain resource use. No arbitrary uploaded courses are accepted.

Build with npm run build:matchmaking (included in npm run build), then run node server/matchmaking-service.mjs /private/matchmaking.json. The private JSON configuration requires port, issuer, audience, jwksUrl, subjects (array of {sub,tenant,name}) and courses (array of {id,project}, where project is canonical project JSON text). The service requires a trusted pinned HTTPS JWKS endpoint with RS256 access tokens and scope race:play. It starts only after keys load and binds to loopback. Configure TLS, reverse-proxy admission/rate limits, security monitoring, real identity provisioning and an appropriate deployment separately.

POST /v1/matchmaking with Authorization: Bearer [access token] and application/json. Actions: join with course; poll with ticket; input with ticket, increasing sequence and {x,z,jump}; leave with ticket. Join is idempotent for the same course. Queued responses return the ticket and course; matched responses return ticket, racer id, canonical project JSON and authoritative snapshot. The original subject must authenticate for every ticket action. Stale inputs are rejected, finished matches return frozen results. Membership expires after 30 seconds of inactivity, matches after five minutes. The service is a single process; distributed scheduling, persistence, public transport, browser sign-in UX, real identity-provider testing and matchmaking beyond two-player static courses remain outstanding.

Regression tests use ephemeral RSA signing keys, actual loopback HTTP, distinct tenant identities, forged claims, stolen tickets, replay rejection, queue quotas, expiry and shared runtime results. The compiled server bundle has an additional Node integration test using pinned-key configuration. No live provider/deployment or acceptance points are claimed before CI and external acceptance.
